# iOS specifics

The iOS module (`modules/plaud-sdk/ios/PlaudSdkModule.swift` + `ios/PlaudWifiController.swift`)
deliberately exposes the same JS surface, event names and payload shapes as Android. This file
covers the places where the platform underneath genuinely differs — read it before wiring up Wi-Fi
fast transfer, debugging a join failure, or replacing the frameworks.

## How it's wired

The SDK ships as three precompiled `.xcframework`s — `PlaudBleSDK`, `PlaudDeviceBasicSDK` and
`PlaudWiFiSDK` — vendored by `ios/PlaudSdk.podspec` via `vendored_frameworks`. CocoaPods embeds and
code-signs them automatically; the `PlaudDeviceBasicSDK.bundle` of localized strings is nested
inside its framework, so it comes along for free with no `resource_bundles` entry. Expo autolinks
the module from `modules/`, so there is **no Podfile or Xcode edit to make by hand**.

`podspec` also lists `NetworkExtension`, `CoreLocation` and `SystemConfiguration` under
`s.frameworks`. The SDK reaches for all three internally on the Wi-Fi path, and `static_framework`
pushes that linking onto the host target.

**arm64 only, iOS 15.1+.** There is no simulator slice — `npx expo run:ios --device`.

### Two `NSObject`s, not one module

Expo's `Module` base class isn't `NSObject`-derived, so it can't conform to the SDK's `@objc`
delegate protocols. Both delegates therefore live in their own classes, wired with an `emit` closure
the module hands in:

- `PlaudSdkController` — `PlaudDeviceAgentProtocol`: scan, connect, file list, BLE export.
- `PlaudWifiController` — `PlaudWiFiAgentProtocol`: the whole Wi-Fi session.

`bleWiFiOpen` arrives on the *BLE* delegate but belongs to the Wi-Fi session, so `PlaudSdkController`
forwards it. That is the only cross-controller call.

## Wi-Fi fast transfer

### Configuration (the one feature that needs it)

`ios/` is generated by `expo prebuild`, so this goes in `app.json`:

```jsonc
"ios": {
  "entitlements": {
    "com.apple.developer.networking.HotspotConfiguration": true,
    "com.apple.developer.networking.wifi-info": true
  },
  "infoPlist": {
    "NSLocalNetworkUsageDescription": "…transfer recordings over Wi-Fi.",
    "NSLocationWhenInUseUsageDescription": "…identify and join your recorder's hotspot."
  }
}
```

**`HotspotConfiguration` is provisioning-profile-gated.** It has to be enabled on the App ID in the
Apple developer portal, and a **free personal team cannot enable it** — signing fails outright. This
is the first thing to check when a build that previously worked stops signing.

Three runtime permissions, in the order they bite:

1. **Location, When-In-Use** — `NEHotspotConfiguration` requires it on iOS 13+; without it the join
   fails with no useful reason. `startWifiTransfer` requests it *before touching BLE* and rejects
   `ERR_PLAUD_WIFI_PREREQ` when it has been denied. Once denied, iOS never re-prompts — send the
   user to Settings.
2. **Local Network** — iOS prompts the first time the SDK binds its WebSocket. There is no API to
   pre-request it. A denial shows up as a `wifiError` with code 1003 or 1006 during connect.
3. The **`wifi-info`** entitlement is only needed to read the current SSID back.

### ⚠️ Timings and ordering that are load-bearing

These come from the Plaud iOS reference app (`plaud-sdk-public` → `SyncManager.swift`) and each one
was a real bug:

1. **The phone is the WebSocket server.** The recorder opens an AP, the phone joins it, and then the
   *device* dials back in. That is why the flow is open-AP → join → wait for the device.
2. **`wholeName`, not `wifiName`.** `bleWiFiOpen` delivers both; the short one will not join.
3. **Assign `bleDevice` inside `bleWiFiOpen`,** not at session start — the SDK's own header docs say
   so. `PlaudWiFiAgent.shared.bleDevice = BleAgent.shared.bleDevice`.
4. **Wait ~3 s after `bleWiFiOpen` before `connectWifi`,** and pass a **180 s** join budget rather
   than the 60 s default. The module backs this with a 185 s watchdog.
5. **`wifiHandshake(0)` is the authority** on "channel usable". A join-failure callback arriving
   after that point is stale and must be ignored, or a working transfer gets flipped to failed.
6. **Never delete between two exports** — it disrupts the WebSocket and stalls the next file. Batch
   every `deleteWifiFiles` after the last transfer.
7. **Don't force-close after the last file.** The device exits on its own after ~3 heartbeats and
   resumes BLE quickly; pre-empting that drops it into a ~2.5 minute fallback. `wifiClose(1000)` is
   the clean ending, including "there was nothing to transfer".
8. **Teardown is a specific three-call sequence:** `setDeviceWiFi(open: false)` → `endWiFiTransfer()`
   → `PlaudWiFiAgent.disconnect()`. `disconnect()` removes the `NEHotspotConfiguration`, after which
   iOS rejoins the network the phone was on before. When the *device* initiated the close, the
   `setDeviceWiFi` call is skipped — `endWiFiTransfer` already asked it to drop the AP, and a second
   close makes it answer with an error. `OnDestroy` runs teardown too, so a JS reload mid-session
   doesn't strand the handset on the recorder's AP with no internet.

BLE **will** drop for the duration of the session — the device gives up the radio to run its AP. An
app that adds its own auto-reconnect has to suppress it while `isWiFiTransferActive`; reconnecting
mid-handshake kills the transfer. (This module has no auto-reconnect, so there is nothing to
suppress today.)

### Derived, not passed through

Android's SDK gives one `IWifiTransferAgent` with a `WifiConnectionState` enum and an
`onError(code, message)`. iOS gives lower-level callbacks and no state type, so `PlaudWifiController`
synthesises what JS sees:

| JS | How iOS produces it |
| --- | --- |
| `wifiState` | Tracked in the controller, derived from `bleWiFiOpen` → `wifiConnectionStatus` → `wifiHandshake` → `wifiClose`. `openingHotspot` is emitted by the module itself, as on Android. |
| `PlaudWifiFile.fileName` | **Synthesised** as `"<sn>-<sessionId>"` — iOS's `BleFile` has no device-supplied name. |
| `PlaudWifiFile.duration` | `BleFile.duration()` is milliseconds; divided by 1000 to match the JS contract. |
| `PlaudWifiFile.timestamp` | `sessionId * 1000` — the session id *is* the recording's unix timestamp. |
| `wifiBattery.charging` | Always `false`; `wifiPower` carries no charging flag. |
| `wifiDeleteComplete` | Aggregated — iOS confirms deletes one file at a time via `wifiFileDelete`, with a 4 s fallback so a missing confirmation still settles the batch. |
| `wifiTransferProgress.speedKBps` | `PlaudWiFiAgent.currentDownloadSpeedKBps`, reported as 0 once `progress` hits 100 (that phase is the local transcode, not the download). |
| `wifiError.code` | **Mapped** onto Android's code space rather than passed through: 1002 open-AP, 1003 join/timeout, 1004 handshake, 1006 connection dropped, 3000 file list, 3001 command rejected. |

`startWifiTransfer`'s `userId` is validated but otherwise unused on iOS — nothing in the Wi-Fi flow
takes one (`getFileList`'s first argument is a request tag, and the module passes a timestamp). It is
still required so a missing id fails identically on both platforms instead of only surfacing when
the app is first tried on a handset.

## Export output

`exportAudio` and `exportAudioViaWiFi` both write to `Documents/PlaudExports`, which is what
`expo-file-system` exposes as `documentDirectory` — the same relative location as Android's
`filesDir/PlaudExports`, so JS-side path handling is identical. Prefix the returned absolute path
with `file://` before handing it to `expo-file-system`.

Use **mp3**. Opus output is unplayable for some decoders and the transcription backend returns an
empty result for it.

## Replacing the frameworks

`plaud-sdk-public/sdk/ios/` ships plain `.framework` bundles; the module vendors `.xcframework`s.
To take a new SDK drop:

```bash
cp -R <src>/<F>.framework staging/<F>.framework
rm -rf staging/<F>.framework/_CodeSignature      # xcodebuild rejects a pre-signed input
xcodebuild -create-xcframework -framework staging/<F>.framework -output <F>.xcframework
```

for each of `PlaudDeviceBasicSDK`, `PlaudBleSDK`, `PlaudWiFiSDK`. Afterwards confirm the version in
`ios-arm64/<F>.framework/Info.plist`, that `PlaudDeviceBasicSDK.bundle` is still nested inside its
framework, and re-test the **BLE** path as well as Wi-Fi — all three binaries move together.
